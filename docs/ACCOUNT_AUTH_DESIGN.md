# 이메일 회원 인증과 중복 방지 설계

2026-09-20. 사용자 결정: 이메일·비밀번호로 시작하고 중복 가입을 방지한다.

상태: 설계 확정 및 외부 인증 연결 준비. 실제 회원가입/로그인 API·화면·마이그레이션은 아직 구현하거나 배포하지 않았다. Supabase 프로젝트 연결과 호스팅 인증 경로 확인 후 구현한다. 현재 사이트는 소유자 전용 비공개이며 공개 전환은 별도 승인 사항이다.

## 책임 경계

- Supabase Auth: 비밀번호 저장/검증, 이메일 소유 확인, 복구 토큰, 인증 세션. 직접 비밀번호 저장소나 자체 해시 방식을 만들지 않는다.
- 기존 D1: 일정, 회차, 준비, 알림 구독·예약·이력, 완료·XP·목표. 이 데이터를 인증 제공자 DB로 이전하지 않는다.
- To J 계정 연결: 인증 제공자의 검증된 식별자를 기존 `owner_id`에 연결한다. 이메일 주소만 보고 기존 기록을 넘기거나 계정을 병합하지 않는다.
- 기존 Sites 인증과 새 이메일 인증이 함께 있는 경우 현재 선택한 로그인 방식을 명확히 구분한다. 이메일 로그아웃 직후 기존 플랫폼 계정으로 조용히 다시 로그인하지 않는다.

## 중복 방지 정책

| 상황 | 처리 규칙 | 최종 방어 위치 |
| --- | --- | --- |
| 이메일 앞뒤 공백·대소문자 차이 | 양끝 공백 제거와 일관된 대소문자 정책으로 비교한다. 제어문자와 잘못된 형식은 거절한다. 실제 제공자 동작과 일치하는지 통합 테스트한다. | 서버 입력 경계 + Auth 고유 계정 |
| 이메일의 점·`+tag` 차이 | 임의로 제거하거나 합치지 않는다. 제공자별 별칭을 근거로 다른 주소를 자동 병합하지 않는다. | 정규화 함수 |
| 같은 이메일로 동시 가입 | 버튼 비활성화는 보조 수단이다. 인증 제공자의 고유 제약을 최종 기준으로 동일 이메일 회원이 하나만 생성되는지 검증한다. | Auth DB |
| 가입 요청 재전송 | 요청 중 재전송을 막고 서버 처리 결과가 불명확하면 일반 안내/재시도 경로를 제공한다. 타임아웃 뒤 새 회원을 임의로 생성하지 않는다. | 서버 요청 처리 |
| 가입됐지만 인증하지 않은 이메일 | 새 To J 계정을 만들지 않는다. 재발송 절차와 대기 시간을 안내한다. 기존 비밀번호·가입 상태를 덮어쓰는 재가입 동작은 허용하지 않는다. | Auth 상태 + 앱 계정 생성 조건 |
| 인증 메일 재발송·복구 요청 | 서버/제공자 제한과 재요청 대기 시간을 적용한다. 여러 탭에서도 제한되며 클라이언트 타이머만 믿지 않는다. | 서버 및 Auth 제한 |
| 같은 인증 사용자의 동시 첫 로그인 | 검증된 `(issuer, subject)`마다 한 연결만 INSERT한다. 충돌 시 기존 연결을 조회하고 새 계정을 만들지 않는다. | D1 고유 제약 + 원자적 처리 |
| 기존 To J 계정에 여러 이메일 계정 연결 | 첫 단계에서는 owner당 이메일 인증 연결 하나만 허용한다. 교체/병합은 제공하지 않고 별도 재인증 흐름으로 다룬다. | D1 고유 제약 |
| 이미 다른 owner에 연결된 인증 사용자 | 연결을 거절한다. 충돌 시 UPDATE로 소유자를 바꾸지 않는다. | D1 연결 INSERT 조건 |
| 재발급 후 이전 인증·복구 링크 | 목적·만료·일회성 소비를 제공자에서 검증한다. 재발급의 기존 링크 폐기 동작도 실제 프로젝트에서 확인한다. | Auth 토큰 검증 |

같은 이메일의 중복 계정을 방지하는 것이 목표다. 한 사람이 여러 실제 이메일 주소로 가입하는 것을 완전히 식별·차단하는 기능은 아니며, 이를 위해 추가 개인정보를 수집하지 않는다.

## 사용자 흐름

1. 가입: 이메일, 비밀번호, 비밀번호 확인 입력 → 서버 검증 → 인증 메일 안내. 미인증 상태에서 일정/XP 계정을 생성하지 않는다.
2. 인증: 메일의 일회성 확인 절차 → 인증 완료 안내 → 로그인. 이메일 검사 자체를 기존 계정의 연결 승인으로 취급하지 않는다.
3. 로그인: 비밀번호 검증과 이메일 인증 여부 확인 → 서버 검증된 식별자 조회 → 단일 To J 계정 연결 → 오늘 화면. 사용자 ID를 요청 본문이나 로컬 저장소에서 신뢰하지 않는다.
4. 기존 기록 연결: 기존 플랫폼 계정으로 로그인한 상태에서 연결을 명시적으로 시작한다. 짧은 유효기간의 서버 상태/CSRF 방어와 새 이메일 계정 재인증을 거친 뒤 양쪽 계정 소유를 확인한다. 이메일 일치만으로 자동 연결하지 않는다.
5. 비밀번호 분실: 계정 존재 여부와 관계없는 일반 안내 → 유효한 복구 절차 → 새 비밀번호 설정. 복구 링크를 계정 연결 권한으로 사용하지 않는다. 기존 세션 폐기 정책을 확인하고 구현한다.
6. 로그아웃: 선택된 앱 세션을 폐기하고 개인 화면·메모리 캐시·계정별 로컬 열람 위치를 정리한다. 알림 수신 설정의 유지/해제는 별도 설명과 선택으로 구분하며 다른 기기의 동의를 임의로 바꾸지 않는다.

## 기존 데이터 연결 구조

예정 테이블 `account_identities`:

- `issuer`: 고정된 인증 프로젝트/제공자 식별자. 클라이언트 입력으로 선택하지 않는다.
- `subject`: 제공자가 검증한 불변 사용자 ID.
- `owner_id`: 현재 데이터가 사용하는 To J 소유자 ID. 새 사용자에게만 새 값을 발급한다.
- `provider`: 첫 버전 `supabase_email`.
- `created_at`: 서버 연결 시각.
- `UNIQUE(issuer, subject)`와 `UNIQUE(owner_id, provider)`로 양쪽 중복 연결을 막는다. `INSERT` 충돌 시 기존 연결을 확인하되 재할당하지 않는다.

기존 `events`, `push_subscriptions`, `notification_jobs`, `notification_deliveries`, `occurrence_completions`, `xp_ledger`, `daily_goals`, `route_request_limits`의 `owner_id`는 변경하지 않는다. 기존 알림 서명에도 owner가 포함되므로 새 인증 ID를 곧바로 owner로 대체하지 않는다. 계정 연결은 기기 구독 이동/재동의/XP 재지급을 실행하지 않는다.

## 보안과 안내

- 공개 이메일 중복 확인 API를 만들지 않는다. 가입/복구 응답으로 특정 이메일의 가입 여부를 조회할 수 없도록 본문·상태·응답 시간 차이를 검토한다. 로그인 실패는 ‘이메일 또는 비밀번호를 확인해 주세요’로 묶는다.
- 비밀번호·세션·인증 링크를 로그에 남기지 않는다. 비밀번호를 평문, 브라우저 저장소, D1에 저장하지 않는다. 클라이언트에는 관리자/service-role 키를 전달하지 않는다.
- 비밀번호 정책은 공백/유니코드 허용·충분한 길이·전체 길이 검증·임의 잘라내기 금지를 원칙으로 제공자 설정과 맞춘다. 구체적인 최소/최대 길이는 연결한 프로젝트 설정을 검사한 뒤 고정한다.
- 브라우저 세션/서버 API 통합은 제공자의 공식 현재 지원 흐름을 사용한다. 토큰의 서명/발급자/수신자/만료와 서버 사용자 검증 없이 디코딩 결과만 믿지 않는다. 세션 저장 방식과 로그아웃/복구 후 폐기 범위를 구현 전에 고정한다.
- 상태 변경 요청의 동일 출처·CSRF 방어, 안전한 쿠키 속성, 고정된 리다이렉트 허용 목록을 적용한다. Sites 예약 경로 `/signin-with-chatgpt`, `/signout-with-chatgpt`, `/callback`은 재정의하지 않는다.
- `oai-authenticated-*` 헤더는 기존 신뢰된 Sites 경계에서만 사용한다. 다른 호스트로 옮길 경우 외부에서 이 헤더를 주입해 로그인할 수 없도록 해야 한다. 개발용 `local-preview` fallback은 공개 환경에서 활성화하지 않는다.
- 로그인 제한은 이메일/신뢰 가능한 요청 출처/전체 처리량을 함께 고려하며 인증 제공자를 직접 호출해도 보호되는 CAPTCHA·제공자 제한을 검토한다. 영구 계정 잠금으로 타인이 사용자를 차단할 수 있게 만들지 않는다.

## 구현 전 연결 항목

1. Supabase 연결 후 사용할 프로젝트를 확인한다. 새 프로젝트가 필요하면 계정·리전·비용을 확인한 후 생성한다. 다른 프로젝트를 임의로 재사용하지 않는다.
2. 이메일 인증 켜짐, 회원가입 정책, 비밀번호 정책, 재발송/검증 제한을 확인한다.
3. 사이트 주소와 정확한 인증/복구 리다이렉트를 설정한다. 공개/비공개 호스팅에서 메일 링크의 전체 경로가 동작하는지 검증한다. 현재 소유자 전용 접근 권한은 승인 없이 바꾸지 않는다.
4. 실제 사용자 메일 발송을 위한 SMTP와 발신 도메인을 구성한다. Supabase 기본 메일 발송은 운영용이 아니며 팀에 등록된 주소 중심의 제한이 있다.
5. 프로젝트 URL/공개용 키와 필요한 서버 비밀값은 환경 설정에만 등록한다. 사용자 비밀번호나 관리자 비밀키를 대화에 붙여넣도록 요청하지 않는다.

## 통과해야 하는 검증

- 동일 이메일의 표기 변형·동시 20회 가입·응답 유실 뒤 재시도에도 인증 사용자/To J 연결 각각 하나.
- 점/`+tag`가 다른 주소는 자동 병합되지 않으며 Unicode 유사 문자와 제어문자도 모호하게 정규화되지 않음.
- 미인증 사용자의 로그인·직접 API 호출은 차단되고 일정/XP 계정이 생성되지 않음.
- 가입 여부가 다른 이메일의 가입/복구 안내가 계정 존재 여부를 노출하지 않음.
- 인증/복구 링크 만료·재사용·목적 교체·재발급·여러 탭 요청이 안전하게 처리됨.
- 두 기기의 동시 첫 로그인과 두 기존 계정의 동시 연결 시 중복 생성/소유자 재할당 없음.
- 기존 기록 연결 전후 일정, XP, 목표, 구독 동의, 예약/발송 이력과 기존 알림 버튼이 유지됨.
- CSRF·오픈 리다이렉트·위조 사용자 헤더·변조/만료 세션·다른 계정 접근 차단.
- 로그아웃/복구/인증 서비스 장애 시 개인 데이터 노출·기존 플랫폼 계정으로 자동 우회 없음.
- 기존 13개 회귀 테스트 및 새 인증 통합 테스트, 실제 테스트 이메일 가입→인증→로그인→복구→로그아웃 확인.

위 목록은 통과 결과가 아니라 구현 완료의 검증 기준이다.

## 확인한 공식 자료

- [Supabase 이메일·비밀번호 인증](https://supabase.com/docs/guides/auth/passwords): 가입·로그인·이메일 확인·비밀번호 복구 흐름.
- [Supabase 가입 API](https://supabase.com/docs/reference/javascript/auth-signup): 기존 계정 정보 노출을 방지하는 응답에 유의하며 가입 응답만으로 새 회원 생성을 단정하지 않는다.
- [Supabase 요청 제한](https://supabase.com/docs/guides/auth/rate-limits): 인증 및 메일 관련 서버 제한과 429 처리. 실제 값은 연결 프로젝트에서 확인한다.
- [Supabase SMTP 설정](https://supabase.com/docs/guides/auth/auth-smtp): 기본 발송의 제한과 운영용 메일 연결.
- [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html): 계정 존재 여부 노출과 인증 공격 방어.
