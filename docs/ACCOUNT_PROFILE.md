# 아이디·닉네임

2026-09-20. 이메일·비밀번호 인증 연결과 별개로, 기존 Sites 로그인 계정에 프로필을 추가한다. username은 현재 로그인 자격 증명이 아니라 고유한 회원 표시 ID다. 닉네임을 변경해도 일정, 알림, XP의 owner_id는 바뀌지 않는다.

## 정책

- 아이디: 최초 한 번 설정, 변경 불가. 영문으로 시작하는 4~20자, 영문·숫자·밑줄. 양끝 공백 제거 및 소문자 저장. DB UNIQUE로 중복을 막으며 운영용 예약어는 거절한다.
- 닉네임: 2~16자, 한글 완성형·호환 자모·영문·숫자·밑줄. NFC 정규화와 양끝 공백 제거 후 검사. **중복 불가**이며 영문 대소문자를 구분하지 않는다. 표시 대소문자는 보존한다. 공백·이모지·제어문자 불가.
- 최초 설정 및 실제 변경부터 30 × 24시간 대기. 같은 닉네임 재저장과 실패한 변경은 시간을 갱신하지 않는다. 정확한 다음 변경 시각은 한국 시간으로 표시한다.
- 원하지 않는 강제 설정은 없다. 미설정 상태에서도 기존 일정을 사용할 수 있다.

## 구현

`/profile`에서 최초 설정·변경 확인을 거친다. 홈 상단 프로필 아이콘과 데스크톱 사이드바에서 진입한다. 긴 정책 설명은 상세 펼침에 둔다.

`GET /api/profile`은 본인의 프로필 또는 null을 반환한다. `POST` 본문은 username/nickname, `PATCH` 본문은 nickname/revision만 허용한다. owner_id는 서버의 인증 결과만 사용하며 요청 본문으로 받지 않는다. 기존 개발용 local-preview는 개발 모드에 한정된다.

`account_profiles`의 owner PK와 username UNIQUE가 동시 등록의 최종 기준이다. 변경은 owner·revision·DB 현재 시각 기준 쿨다운을 단일 UPDATE에서 검사한다. 같은 값의 재전송은 no-op이며, 다른 기기의 오래된 화면은 409로 충돌을 안내한다. 프로필 삭제나 아이디 재할당 API는 제공하지 않는다.

닉네임은 `UNIQUE lower(nickname)` 인덱스가 최초 설정과 변경 모두에서 최종적으로 중복을 차단한다. 허용 영문이 ASCII이고 저장 전에 NFC 정규화를 하므로 DB와 입력 경계의 비교 방식이 일치한다. 중복 시 409 `nickname_taken`을 반환하며 다른 사람의 계정 정보를 반환하지 않는다. 화면은 작성 내용을 유지하고 닉네임을 수정할 수 있게 한다. 실패한 변경은 닉네임·revision·30일 대기 시작 시각을 갱신하지 않는다. 자신의 대소문자만 수정하는 것은 실제 표시 변경이므로 30일 규칙을 적용한다.

새 인덱스는 기존 프로필을 수정하거나 삭제하지 않는다. 적용 전 실제 프로필의 중복 및 정규화 상태를 확인하며, 기존 중복이 발견되면 임의로 이름을 바꾸지 말고 해결 정책을 먼저 정한다. 다른 이름으로 변경을 완료하면 이전 닉네임은 다른 회원이 사용할 수 있다. 별도 닉네임 예약/보호 기간은 없다.

Origin 일치·비표준 요청 헤더·JSON Content-Type·2KB 요청 한도를 적용하고 응답은 private/no-store다. 다른 사람의 아이디·이메일 조회 API는 없다. 변경 실패/응답 유실 시 입력을 유지하고 현재 정보 재확인을 요구하며 자동 재저장하지 않는다.

프로필 미설정 상태에서도 GET은 현재 owner의 목적별 SHA-256 `accountScope`를 반환한다. 저장 요청의 헤더와 서버가 현재 로그인 계정으로 다시 계산한 값을 비교하여, 다른 탭에서 계정을 바꾼 뒤 이전 계정 화면으로 새 계정에 저장하는 실수를 차단한다. 이 값은 비밀 인증 토큰이 아니며 owner 선택이나 로그인 권한으로 사용하지 않는다.

## 검증과 향후 연결

`node scripts/test-account-profiles.mjs`는 빌드된 Worker와 격리 D1에서 정규화·권한·중복·30일 경계·동시 변경·재시도·장애를 검사한다. 사용자 데이터 및 실제 인증 계정은 변경하지 않는다.

이메일 인증 연결 시 검증된 계정 매핑을 통해 기존 owner_id를 유지해야 한다. 아이디로 로그인하는 기능을 도입할 경우 비공개 username→인증 계정 해석, 로그인 시도 제한, 일반화된 실패 응답을 별도로 구현해야 한다. 닉네임으로는 로그인하거나 계정을 연결하지 않는다. 공개 출시 전에 개인정보 처리방침의 수집 항목·보유 기간에 아이디/닉네임을 반영한다.

구현 참고: [Cloudflare D1 prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/), [OWASP CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). 현재 로그인 공급자 및 비밀번호 재설정 준비 로직은 변경하지 않았다.
