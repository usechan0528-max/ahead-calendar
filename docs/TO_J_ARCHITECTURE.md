# To J — 공통 제품 규칙과 모바일 확장

기준: 2026-09-19. 이번 구현은 기존 비공개 웹 서비스의 첫 성장 기능이다. iOS/Android 앱이나 별도 공개 회원 체계가 완성된 상태는 아니다.

## 제품 규칙 v1

- 계획 첫 완료 10 XP, 준비 항목의 회차별 첫 완료 3 XP, 오늘 목표 달성 10 XP.
- 하루 전체 합계는 60 XP. 부분 지급 가능(예: 59 XP에서 계획 완료 시 1 XP). 상한 이후에는 0 XP 완료 영수증을 저장한다.
- 날짜는 클라이언트가 아닌 서버의 한국 시간(KST)으로 결정한다. 영수증에는 최초 완료일을 고정한다.
- 취소는 체크 상태만 되돌린다. 획득 XP와 최초 완료 횟수는 유지한다. 다시 체크하거나 기기를 바꿔도 같은 회차에서 재지급하지 않는다.
- 원본 일정·준비 항목 삭제도 이미 얻은 XP를 삭제하지 않는다. 알림 확인은 계획 완료가 아니며 XP를 주지 않는다.
- 오늘 목표 1~5개, 기본 3개. 당일 첫 계획 완료 영수증이 생기면 목표가 고정된다. 준비만 완료한 상태에서는 목표 변경 가능하다.
- 과거 계획을 오늘 처음 완료해도 오늘 상한과 목표에 포함된다. 미래 일정은 완료할 수 없으며 시간 지정 일정은 실제 시작 시각부터 허용한다.
- 준비는 과거·오늘 또는 다음 회차에 미리 완료할 수 있다. 멀리 있는 여러 미래 회차를 한 번에 완료하지 못한다.
- 여러 날 일정의 식별자는 반복 회차의 시작일이다. 화면의 날짜 칸마다 별도 보상하지 않는다.

## 성장 곡선

50레벨이며 레벨 50은 정확히 12,000 XP에서 시작한다. `lib/progression.ts`의 `LEVEL_THRESHOLDS`가 유일한 기준이다.
레벨 n(1~50)의 필요 누적 XP는 `round(20*(n-1) + 11020*((n-1)/49)^2)`다.
1~10 P, 11~20 P+, 21~35 PJ, 36~49 J−, 50 J. 도착 후에도 XP를 기록하며 레벨은 50으로 표시한다.
최단 200일, 하루 평균 40 XP 가정 시 300일. 이는 규칙에 따른 계산이며 실제 사용자 유지율 예측이 아니다.
누적 실천일 1/7/30/100일 배지를 제공한다. 쉬는 날 감점은 없다. 2026-09-20에 10개 챕터·50개 레벨 이름·5레벨마다 획득하는 칭호와 성장 카드 디자인을 추가했다. 칭호·배지는 추가 XP를 주지 않으며 서버 누적 기록에서 파생한다. 캐릭터 꾸미기나 기능 잠금은 없다. 상세는 `LEVEL_DESIGN.md`를 참조한다.

## 데이터와 안전성

- `occurrence_completions`: 계정·일정·회차 시작일·종류·항목 ID별 상태. 일정 삭제 시 상태만 정리한다.
- `xp_ledger`: 계정·행동 키 유일 제약이 있는 불변 보상 기록. 원본과 cascade FK를 연결하지 않는다.
- `daily_goals`: 계정·KST 날짜별 목표. 목표 잠금은 당일 event 영수증 존재 여부로 판단한다.
- 완료 저장, SQL 합산 기반 XP 지급, 목표 보너스, 해당 회차 대기 알림 취소를 하나의 D1 batch 트랜잭션에서 실행한다.
- 동일 요청 경합과 서로 다른 완료의 경합 모두 DB에서 상한을 계산한다. 0 XP 기록도 남겨 다음 날 재전송으로 지급받지 못하게 한다.
- 이벤트 revision을 확인하여 편집된 일정의 이전 검증 결과로 보상하지 않는다.
- 기존 공유 준비 완료는 원래 첫 회차에만 표시하고 XP는 소급 지급하지 않는다. 변경 전에 `legacy_completed_date`를 고정해 날짜 편집·이전 클라이언트의 상태 변경으로 이력이 이동하지 않게 한다.
- 완료 회차는 알림 계획 생성과 발송 직전 검증에서 제외한다. 이미 외부 전송 중인 알림을 회수할 수는 없다. 완료 취소 후에는 기존 수신 동의·발송 시간 범위·중복 방지 규칙에 따라 다시 계획할 수 있다.

## 현재 API

- `GET /api/progress`: 성장 요약·오늘 목표·완료 회차.
- `PATCH /api/progress`: `{target: 1..5}`. 첫 계획 완료 뒤 변경은 409.
- `GET /api/events/:id/completion?date=YYYY-MM-DD`: 지정 회차의 완료·준비 상태와 지금 완료 가능한지.
- `PATCH /api/events/:id/completion`: `{date, kind: 'event'|'preparation', itemId?, complete: boolean}`. XP·현재 시각·계정 ID를 클라이언트에서 받지 않는다.
- 인증 없는 요청 401, 다른 계정 일정 404, 잘못된 회차/미래 완료 400, 동시에 수정된 일정/항목 409.

## 모바일 확장 경계

`lib/progression.ts`, `lib/recurrence.ts`, `lib/event-duration.ts`는 React·브라우저·Cloudflare 의존성이 없는 공통 TypeScript다.
`db/progress.ts`는 DB와 확인된 사용자 ID를 인자로 받는다. 인증은 API 경계의 기존 Sites 인증이 맡는다.
`components/use-growth.ts`는 웹 통신·상태, 컴포넌트는 웹 표시를 맡는다. 네이티브 앱은 공통 규칙과 응답 계약을 사용하되 화면과 기기 알림 계층을 별도로 구현한다.

다음 단계:

1. iOS/Android에서 한 일정의 로컬 알림·원격 푸시·취소·앱 종료·재부팅·권한 거부를 실기 검증한다. 앱 빌드/계정/비용 선택은 해당 단계에서 결정한다.
2. 기존 계정을 보존하는 To J 사용자 식별자 매핑과 앱 인증을 설계한다. 현재 Sites 헤더를 앱에서 위조·전송하는 방식은 사용하지 않는다. 플랫폼 토큰을 앱에 넣지 않는다.
3. 오프라인 완료 큐와 서버 동기화를 추가한다. 일일 상한·XP 확정은 서버가 소유하고, 오프라인 기록의 인정 날짜/시간대 변경 정책을 먼저 정한다.
4. 로컬 알림과 서버 푸시의 기기별 책임, 회차 ID, 취소·중복 방지 계약을 정의한다. OS의 백그라운드 실행이나 정확한 도착을 무조건 보장하지 않는다.
5. 앱·웹 공통 회원 탈퇴/자료 삭제, 인증 만료, 개인정보·알림 동의 및 스토어 요건을 출시 전에 검토한다.

현재 미구현: 네이티브 앱, 앱용 인증, 오프라인 동기화, 외부 캘린더 동기화. 회차별 날짜·제목 수정/취소와 반복 종료일은 웹에 구현했으며 계약은 `PRODUCT_SPEC.md`를 따른다.
기존 URL, Web Push 동의, 발송 키와 내부 `ahead` 프로토콜명은 호환성을 위해 유지한다. 새 공유 이미지는 요청하지 않아 기존 이미지를 보존했다.

## 사용자 흐름 확장 (2026-09-20)

- `lib/user-journey.ts`는 기존 원회차 계산으로 지난 7일/내일/이어보기 대상을 정한다. 브라우저 기록은 허용된 ID·날짜·상세 영역만 기억하며, 화면 데이터와 완료/XP는 현재 사용자의 서버 응답이 진실의 원천이다. 네이티브 확장 시 화면 계층과 로컬 저장소 어댑터를 교체할 수 있다.
- `POST /api/notifications/jobs/:id/snooze`는 선택형 `{minutes:10|30|60}`를 받는다. 기존 본문 없음 또는 토큰만 보낸 클라이언트는 10분을 유지한다. 토큰 인증과 본문 파싱을 모두 수행하며 이전 소유권·수신 동의·회차 유효성·원자적 갱신 조건은 유지한다. 일정 시작/종료나 완료/XP는 변경하지 않는다.
- 알림 본문 클릭은 화면을 여는 동작이고 명시적 `ack`만 확인 기록을 남긴다. UI 조회/갱신 세대와 선택 식별자를 검사해 늦은 응답으로 다른 일정이나 새 상태를 덮지 않는다.
- 추천 채택은 선택적 1~60자 `timing` 메모를 받을 수 있다. 새로 채택한 준비에만 반영하고 기존 제목·시점·완료는 보존한다. 단계 선택은 기존 채택 트랜잭션과 삭제 식별자를 재사용하며 별도 알림이나 보상 트랜잭션을 만들지 않는다.
- 이번 확장에는 DB 마이그레이션, 외부 유료 API, 개인정보 저장 범위 확대, 기기 자동 동의 변경이 없다. 실기 푸시와 앱 종료/재부팅 검증은 네이티브 단계에서 별도로 수행한다.
